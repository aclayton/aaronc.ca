vesica

One installer that gives every developer on a team the same agent setup: team rules, shared skills, role agents and model configuration for Claude Code, OpenCode, Copilot CLI, Codex and Hermes — with a personal vault the agents use as shared memory.

What this page is. A drawing of the code that exists in the repository today, taken from its own architecture and onboarding notes rather than from the plan. The plan is larger than the code, and the difference is the most useful thing on this page — so it is drawn rather than omitted. The project describes itself as a prototype that should not yet be pointed at a real profile.

On this page: the boundary · the executable flow · the crates · the safety ledger · the rename · what is missing · what was measured.

The boundary

The whole design is one rule: the installer holds no team content. Everything a team writes lives in a separate shared-home repository, and the installer's only job is to wire that repository into each machine. Privacy is a property of where the content lives, not of a policy about who may read it.

The shared home

a separate, usually private repository

  • Agents/ — skills, roles, conventions
  • Knowledge/ Decisions/ Standards/
  • Templates/ Repos/
  • agent-home.toml and a catalog
Holds all team content. Removing the installer leaves this intact; that is the point of the split.

Why the split is drawn this way. The installer repository is public and contains nothing worth protecting, so it can be shared, forked and read by anyone. The content that must not leak never enters it. The privacy comes from the shape rather than from discipline — which is the only kind that survives a busy week.

The executable flow

Six commands, of which three write and three only read. The writing ones share a transaction.

commandwhat it doeswrites?
doctor Parses the team config and catalog; reports WSL status; can emit a JSON report and list the repositories a profile claims. no
install Builds a plan, preflights the destinations, backs up existing instruction files, executes the supported actions, saves the manifest. yes
status Reads the install manifest and reports the entries it records. no
uninstall Verifies hashes and links, then removes or restores only what it can verify. Anything modified or ambiguous is kept and reported. yes
lint Read-only checks over a shared home, with diagnostics that never print the matched text. no
vault-scan Recursively checks bounded-size UTF-8 files for common credential patterns, by path and line only. no

What install does, in order

  1. 01

    Plan

    The team config and catalog are parsed and validated. Credential-like keys are rejected here, before anything touches a disk.
  2. 02

    Preflight

    Every planned destination and the state directory are checked with symlink-aware metadata. An unmanaged collision, or a manifest-managed target that has been modified, fails closed — the install stops rather than proceeding.
  3. 03

    Back up

    Existing Claude and Codex instruction files are backed up before any managed block is added. A repeat install reuses the backup it already recorded.
  4. 04

    Execute

    The supported actions run: the ~/Team symlink, the managed imports, the skill links. Symlinks are only ever created at an absent destination, or accepted if they already point the right way.
  5. 05

    Commit the manifest

    Targets, source paths, backups and hashes are written to the manifest through a unique temp file, restrictive permissions, a flush, then a rename. Steps 04 and 05 share one rollback transaction: if the manifest cannot commit, the actions are reversed in order.

The lint rules, by id

Diagnostics carry a relative path, a line number and one of these ids — never the matched text. The check is a heuristic, and the project says so: a clean scan is not proof that a vault holds no secrets.

The safety ledger

The nine rules the installer holds itself to. They are all of the same kind: refuse to guess, record what was done, and never destroy something that changed underneath you.

  1. The shared home holds team content; the installer repository holds none.
  2. Parsing rejects credential-like keys before any action is planned.
  3. All destinations and the manifest are preflighted with symlink-aware metadata. An unmanaged collision, or a managed target that was modified, fails closed.
  4. Existing instruction files are backed up before managed blocks are written. A repeat install reuses its recorded backup.
  5. Action execution and manifest persistence share one rollback transaction. If the commit fails, actions are reversed in order, and intervening edits are reported rather than overwritten.
  6. Manifest writes go to a uniquely created temp file, with restrictive permissions, then flush, sync and rename. A pre-existing temp file or symlink is neither followed nor replaced.
  7. The manifest records targets, sources, backups and hashes. Uninstall touches only entries it can verify; modified or ambiguous content is retained and reported.
  8. Symlinks are created only where nothing exists, or accepted if already correct. An existing user destination is never replaced.
  9. Secret-scan output contains locations only. Files are capped at 2 MB and symlinks are not traversed.

The limit of the guarantee, in the project's own words. The transaction cannot succeed if the operating system refuses a rollback, or if a user replaces a file at the same moment. Rollback is best-effort: it preserves and reports what it finds, and a rollback error may still leave partial state. Windows and WSL end-to-end behaviour is unverified.

The rename, and what still carries the old name

The installed program is vesica. The paths that an existing install depends on were deliberately not renamed, so that an earlier installation is not orphaned. The result is a compatibility table rather than a clean sweep — and the historical identifiers are the ones that matter to anyone migrating.

Renamed

  • ›The CLI and the installed binary: vesica
  • ›The repository name, and the product identity
  • ›The environment variables read first: VESICA_*
  • ›Uninstall understands both the old and the new managed blocks

Still on the old name, on purpose

  • ×The shared-home config: agent-home.toml
  • ×The manifest: ~/.config/agent-home/manifest.json
  • ×Legacy variables still accepted: AGENT_HOME_REPO, AGENT_HOME_ROOT, AGENT_HOME_ALLOW_NON_WSL
  • ×The internal crate prefixes, ah-*

One exception worth knowing. Every other path here keeps the old name for compatibility, but the public download URL does not. The README's install command points at a version tag that does not exist yet, so the command in the repository's own front page currently fails. That is a release-publishing gap, not a rename problem — see what was measured, below.

What is missing

This is the most important section on the page. The plan describes a complete multi-agent installer for Windows and WSL; the code is a working local slice of it. Drawn side by side, because a drawing that hid the gap would be a worse drawing.

Wired and working

  • ›The ~/Team symlink from the shared home
  • ›Managed instruction blocks for Claude Code and Codex
  • ›Skill-directory discovery, linked into .agents/skills and .claude/skills
  • ›The full install / status / uninstall cycle, with a manifest
  • ›Read-only lint and the credential scan
  • ›Profile selection, recorded and reported
  • ›WSL detection, with a CI override

Named in the plan, not in the code

  • ×Harness wiring for OpenCode, Copilot CLI and Hermes — three of the five named agents
  • ×Role-agent rendering, Foundry setup and probes, and Herdr
  • ×Cloning a private team home; profile-specific repository installation
  • ×Per-profile skill selection — every profile currently links the same set
  • ×Windows profile discovery, drvfs and OneDrive validation, winget, Obsidian, scheduled tasks
  • ×Update, signed release verification, and a full multi-action rollback
  • ×Any end-to-end Windows and WSL validation at all

What the project says must happen before a real pilot. Resolve the private-repository and Foundry prerequisites; finish the missing integrations and their tests; run it on a disposable Windows and WSL profile; verify the release artifacts; and obtain explicit release approval. That list is the project's own, and it is the honest answer to “can we use it yet” — no.
